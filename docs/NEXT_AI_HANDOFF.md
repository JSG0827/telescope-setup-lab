# 다음 AI를 위한 실행 지침 — 망원경 설치 실험실

기준: 2026-09-07 로컬 v8. **여기 적힌 T01 이후 작업은 아직 구현하지 않았다.**

이 파일과 [전 과정 점검 보고서](END_TO_END_AUDIT_2026-09-07.md)를 읽으면 대화 기록이 없어도 다음 작업을 시작할 수 있다. 현재 소스가 달라졌으면 파일·함수를 먼저 검색하여 기준 차이를 기록한다. 줄 번호는 변경될 수 있으므로 함수/컴포넌트를 기준으로 찾는다.

## 1. 작업 전에 반드시 확인

1. 루트 `AGENTS.md`, `docs/DEVELOPMENT_DIRECTION.md`, `docs/CURRICULUM_V2.md`를 읽는다.
2. 실제 코드를 쓸 때 관련 Next.js 가이드를 `node_modules/next/dist/docs/`에서 읽는다. 이 프로젝트는 Next 16.3.4 계열이다. Astro 프로젝트가 아니다.
3. `git status --short`를 확인한다. 기준 시점에는 6·7단계 로컬 변경이 아직 미커밋 상태였다. 사용자 변경을 지우거나 덮어쓰지 않는다.
4. 현재 작업이 보고서인지 구현인지 배포인지 구분한다. 사용자가 구현을 요청해도 별도 요청 없이 push/배포하지 않는다.
5. 저장 버전은 현재 v8. 구버전 키를 삭제하거나 옛 완료를 새 학습 성취로 인정하지 않는다.

## 3. 유지해야 할 계약

- 관찰→판단→조작→재확인. 안전 설명은 즉시 제공하되 정답 방향은 기본 피드백과 구분한다.
- 그림과 히트박스가 같은 좌표·변환을 사용한다. x/y를 CSS 여러 곳에 따로 복제하지 않는다.
- 드롭 성공≠완전 안착≠고정≠시험 완료. 현재 구분을 합치지 않는다.
- 한 축씩 통제한다. 무게추 위치 고정과 축 클러치는 서로 다른 장치다.
- 최종 균형은 관측 부속품을 포함한다. 6·7단계에 부속품을 다시 장착하지 않는다.
- 키보드 대체를 유지하고 동일 reducer 검증을 적용한다. 드래그 정확도를 학습 점수로 삼지 않는다.
- 생성형 이미지가 필요한지 먼저 판단한다. 기존 그림 분할/변환으로 해결되는 문제에 독립 시점의 새 그림을 덧붙이지 않는다.
- 가상 수치는 가상이라고 표시한다. 실물 모델이 없으면 나사 개수·회전 방향·힘을 일반화하지 않는다.
- ‘힌트 0회’는 독립 수행의 증거가 아니다. 자동으로 제공한 행동 지시도 기록해야 한다.

## 4. 구현 티켓

아래 순서는 권장안이다. **한 번에 T01 하나부터** 구현하고 시각 검증까지 마친 뒤 다음으로 간다. 예상 시간보다 합격 조건을 우선한다.

### T01 — 삼각대 드롭 형상과 기준점 일치

관련 문제 A01. 수정 후보: `components/tripod-lesson.tsx`, 필요 시 새 순수 좌표 함수와 테스트 파일. 참고: 다른 부품의 실제 기준점 판정 구현.

현재: `inside(x,y)`가 `getBoundingClientRect()`의 사각형만 검사한다.

권장 구현:

1. 화면의 타원 중심 `(cx,cy)`, 반지름 `(rx,ry)`을 하나의 계산 결과로 제공한다.
2. 포인터 시작 시 준비물대 부품의 바닥 기준점과 포인터 간 오프셋을 보관한다.
3. 드롭할 때 포인터 자체가 아니라 변환된 부품 바닥 기준점을 사용한다.
4. `((x-cx)/rx)^2 + ((y-cy)/ry)^2 <= 1`로 검사한다. rx/ry<=0, NaN이면 거절한다.
5. 여유 반경이 필요하면 별도 이름으로 정의하고 강조 그림도 동일 크기로 표현한다.
6. 드래그 중 호버 강조와 pointerup 최종 판정을 동일 함수로 통일한다.
7. pointercancel은 배치를 완료하지 않는다. Enter는 명시적인 접근성 대체 설치로 기존 안전 조건을 거친다.

합격 테스트:

- 타원 중심 통과, 사각형 모서리 실패, 충분히 바깥 실패, 경계 규칙 명시.
- 동일 부품을 위/가운데/아래에서 잡아도 같은 최종 바닥 위치면 같은 결과.
- 1280×800, 390×844 및 스크롤 뒤 같은 성질.
- 선행 조건과 취소 동작 유지. 기존 107개 테스트 회귀 없음.
- 수정 전 재현 (481.5,540.2)은 당시 rect의 예시일 뿐이다. 현재 viewport의 실제 rect를 다시 얻어 같은 상대 모서리를 시험한다.

완료 기록에는 바깥 실패/안쪽 성공/키보드 성공의 실제 화면 확인을 남긴다. 좌표 단위 테스트만으로 완료하지 않는다.

### T02 — 세 다리의 펼침 상태를 그림에 연결

관련 A02/A03/A05. 후보: `components/tripod-lesson.tsx`, `components/tripod-rig.tsx`, `lib/tripod-rig.ts`, 해당 CSS 및 tripod 테스트.

우선 기존 spread 상태를 이용해 8개 조합을 표현한다. 새 연속 각도 모델은 필수 아님. 다리 id→힌지/발/라벨→그림 조각을 일관되게 매핑한다. 0/3,1/3,2/3,3/3을 전체 이미지 두 장 교체로 처리하지 않는다.

펼침 지지대 구현은 별도 소티켓으로 둔다. 실제 기준 구조를 확정하지 않고 무조건 트레이 설치를 필수화하지 않는다.

합격: 8개 조합에서 펼친 다리만 해당 위치로 이동, 상판과 다리 분리/겹침 오류 없음, 3/3 이전 지지 확인 차단 유지. 세 다리 전개 후 기존 다리 길이·기포·수평 판정 변화 없음. 장착된 가대가 있을 때 다리 조작 잠금 유지.

### T03 — 접촉·받침·시험의 공통 시각 표현

관련 A06/A07/A11~A14/A18. 처음에는 3단계 무게추 하나만 구현한 뒤 다른 단계로 확장한다.

설계:

- `support` 표시의 기준점을 실제 부품 몸체에 붙인다. 손 일러스트 또는 명확한 지지 접촉 표시를 사용한다.
- 시험 결과는 물리 상태와 분리된 시각 상태(예: `testVisual: none|slip|steady`)로 전달한다.
- 미끄러짐 시험은 실제 영구 위치를 바꾸지 않는 제한된 변위/잔상으로 시작할 수 있다. 이것을 ‘교육용 강조’라고 표시한다.
- 시험에 실패한 위치를 성공 위치로 자동 보정하지 않는다.
- 잠금 상태의 손잡이/나사 표시가 전체와 확대에서 일치해야 한다.
- 모션 감소 설정에서는 애니메이션 대신 전후 윤곽과 방향을 제공한다.

합격: 풀린 나사 시험은 움직임 표시+실패, 잠근 후 시험은 안정+성공, 끝 안전장치만으로 성공 불가, 받침 없이 위험 행동 차단. 애니메이션 완료가 reducer 성공 판정을 대신하지 않아야 한다.

### T04 — 가대 그림과 축별 시험 자세 연결

관련 A08/A15/A21. 후보: mount/observing lesson 및 rig 함수.

먼저 정한다: 화면의 ‘보기’는 카메라만 바꾸는가, 장비 자세도 바꾸는가? 이름과 상태를 분리한다. 예를 들어 `cameraView`와 `pose`를 별개로 두되 명칭은 현재 코드에 맞춘다.

- 전체 장비에서 RA/DEC 축, 잠긴 축, 움직이는 부품을 강조한다.
- 시험 자세 전환은 지지·고정 상태를 검사한다. 잠긴 축이 아무 설명 없이 회전하는 그림을 만들지 않는다.
- 완전 3D 대신 사전에 정의한 2D 포즈와 연결 전환을 사용해도 된다.
- 기존 `moments`, `withinBalance`를 보존하고 회전 방향을 같은 부호에서 얻는다.
- 현재 저울형 모형은 원리 설명 보조로 남기고 실제 가대와 대응선을 제공한다.

합격: RA 시험에서 무게추봉 수평과 회전축이 식별됨, DEC 시험에서 경통 앞뒤와 축이 식별됨, 다른 축 잠금 확인 가능. 동일 질량/위치에서 실제 그림과 모형의 내려가는 쪽이 일치. 다음 단계와 재방문에서도 부속품 누락 없음.

### T05 — 6·7단계 광학 연속성

관련 A19/A20/A24. 후보: alignment/focus 모델·화면, 새 공통 광학 함수, app 연결, 각 테스트.

작은 순서로 수행:

1. 천체의 공통 id, 좌표, 각지름, 시야 반지름을 정의한다. Jupiter와 위성 배치를 두 화면에서 공유한다.
2. 실제 각지름 원반과 학습용 식별 표식을 분리한다. 6단계 `r=7`과 7단계 `rx=2`를 독립 상수로 두지 않는다.
3. 전체 시야의 각크기 비율을 맞춘다. 5× 학습 확대는 렌더링 파라미터이며 장착 접안렌즈 변경이 아니다.
4. 초점 상태의 연속성을 정한다. 최소 수정은 의도적 관측자 변경 안내, 권장 최종 구조는 공통 포커서 상태이다. 연속 장비 설정인데 단계 번호만으로 흐려지게 하지 않는다.
5. 마지막으로 실제 포커서 인출부를 위치에 연결한다. 광학 그림과 기구 그림은 같은 상태를 읽는다.

합격: 같은 방향/시야/확대 조건에서 6→7의 원반 비율·주변 대상 일치. 상태 변화 없는 단계 전환은 초점을 바꾸지 않음. 의도적 연습 조건 변경은 명시되고 새 관찰 증거 요구. 렌더링 수정 후 현재 선명도 판정이 시각과 어긋나지 않는지 직접 확인.

주의: 실제 천체 위치 API 도입이나 새 행성 사진 생성은 선행 조건이 아니다. 광학 반전 방향을 화면마다 임의로 통일하지 않는다.

### T06 — 기본 관찰 피드백과 도움을 분리

관련 A16/A25/A29. 처음에는 `lib/observing-setup.ts`의 test 피드백을 대상으로 한다.

예:

- 기본: ‘무게추 쪽이 내려가려 합니다.’
- 도움 1: ‘축에서의 거리도 회전 효과를 바꿉니다.’
- 도움 2: ‘무게추가 만드는 회전 효과를 줄이려면 축과의 거리를 어떻게 바꿀까요?’
- 도움 3: ‘무게추를 받치고 위치 고정을 풀어 축 쪽으로 조금 옮긴 뒤 재고정·시험하세요.’

안전 차단은 도움 요청 없이 즉시 제공한다. 이미 안전하지 않은 상태에서 관찰 문제를 풀도록 기다리지 않는다.

안내 모드/도전 모드를 도입한다면 모드 전환을 기록하고 과거 도움을 지우지 않는다. 기본 접근성 설명은 독립된 정책으로 명시한다.

합격: 요청하지 않은 방향 정답이 기본 피드백에 포함되지 않음. 도움은 제공 사실과 수준이 기록됨. 힌트 사용 자체를 안전 실패로 표시하지 않음. 모델 계산과 완료 조건 변화 없음.

### T07 — 과정 이벤트와 설치 리포트

관련 A28/A29/A31. 시각 품질 개선과 별도로 먼저 이벤트 설계를 검토한다.

제안 데이터(예시이며 미구현):

```ts
type LessonEvent = {
  seq: number;
  stageId: string;
  action: string;
  outcome: 'applied' | 'blocked';
  reasonCode?: string;
  assistance?: 'observation' | 'principle' | 'action';
  source: 'pointer' | 'keyboard' | 'button' | 'system';
  evidence?: Record<string, string | number | boolean>;
};
```

`message`는 표시용이지 판정 키가 아니다. 이벤트별 evidence 스키마는 가능한 좁게 정의한다. 개인정보/실명은 필요하지 않다. 점수용 반응 시간 수집을 기본으로 넣지 않는다.

리포트 항목:

- 삼각대: 펼침·지지·잠금·최종 수평의 유효 증거.
- 가대/무게추/경통/부속품: 안착·고정·시험, 안전 차단 후 실제 수정 여부.
- 균형: 각 축 시험과 재잠금, 제공받은 도움 수준.
- 정렬: 기준별 확인·두 시야 확인·목성 주경 도입.
- 초점: 현재 조건의 관찰 확인, 학생 진술과 자동 해설 구분.
- 미구현 극축/추적/실물 수행은 ‘미평가’.

합격: 실제 기록 없이 ‘독립 수행’·‘안전 숙련’ 생성 금지. 동일 경고 버튼 반복을 별도 위험 행동 여러 번으로 오해하지 않음. 기록 상한으로 오래된 이벤트가 사라지면 불완전 기록 표시 또는 요약 집계 유지. 로컬 JSON/인쇄용 리포트부터 시작하며 교사 서버는 별도 승인 범위.

### T08 — 필요한 단계만 재연습하는 무효화 정책

관련 A30. 상태 의존성을 표로 만든 후 구현한다.

| 변화 | 최소 재확인 후보 |
| --- | --- |
| 지면/다리 변경 | 상판 안정·수평, 극축 방향 관련 증거 |
| 가대 방위·고도 변경 | 극축 확인·현재 조준; 결합부를 풀었다면 해당 고정 확인 |
| 무게추 위치 변경 | RA 균형 및 최종 잠금 |
| 경통 앞뒤/부속품 구성 변경 | 해당 부품 고정과 두 축 균형 |
| 파인더 조절 | 파인더 정렬 및 목표 도입 확인 |
| RA/DEC 조준 | 현재 목표 도입; 상대 파인더 정렬은 원칙적으로 유지 |
| 포커서 이동 | 현재 초점 관찰·특징·완료 |

이 표는 구현 전 모델별 검토가 필요한 설계안이다. 선행 안전 상태를 무시하고 상위 단계를 바로 편집하게 만들지 않는다. ‘이 변경으로 다시 확인할 항목’을 먼저 설명하고 안전한 작업 자세로 진입한다. 전체 처음부터 초기화로 단순화하지 않는다.

### T09 — 기본 극축 확인·큰 이동·수동 추적 확장

관련 A22/A23/A27. 현재 범위 밖의 신규 기능이므로 구현 전 세부 설계를 사용자와 확인한다.

원하는 학습 결과: 수평과 극축 방향의 차이를 알고, 적절히 설정된 적도의에서 RA 미동으로 시야의 대상을 유지하는 이유를 경험한다. 촬영용 정밀 정렬을 중학생 필수 조건으로 삼지 않는다.

명시적인 장비 프로파일, 위도·북쪽 기준, 시간 정지/진행 상태를 사용한다. 태양/위험 방향은 허용하지 않는다. 극축 조절과 경통 조준을 같은 action으로 처리하지 않는다. 시간 가속을 사용할 경우 표시하고 속도를 평가하지 않는다.

합격: 파인더 정렬만으로 극축 성공 불가, 기본 극축 방향 확인과 목표 탐색 구분, 시간 진행 시 일관된 시야 이동, RA 조작과 반응 방향 검증. 대기 흐림을 포커서 이동만으로 제거할 수 없다는 현재 성질 유지.

### T10 — 문서·레거시·수업 검증 정리

관련 A32/A33. 기능 수정과 레거시 삭제를 한 커밋에 섞지 않는 것을 권한다.

- 현재 실행 분기를 확인한 후에만 미사용 UI를 제거한다. 저장 이행 로직은 별도 검증 없이 삭제하지 않는다.
- 각 모델 문서 상단에 현재 적용 버전/역사 기록을 구분한다.
- 실제 학생 3~5명으로 조작 부위 식별, 실패 원인 설명, 모바일 시야 구별, 소요 시간을 확인한다. 예상 12분은 검증 전 가설이다.
- 20명 수업의 저장/리포트 제출 방식과 새로고침·공용기기 개인정보 정책을 정한 뒤 부하·배포 검증을 수행한다.

## 5. 매 작업의 검증 절차

1. 수정 전 해당 문제를 재현하고 상태를 기록한다.
2. 순수 계산/상태 전이 테스트를 먼저 보완한다.
3. 구현 후 기존 107개를 포함한 관련 테스트를 실행한다. 테스트 수가 증가하면 실제 수를 기록한다.
4. `pnpm build`로 운영 빌드와 `scripts/verify-assembly-build.mjs`를 확인한다. 과거 운영 CSS 누락 회귀를 막는 검사다.
5. 운영 빌드 서버의 별도 origin에서 UI를 확인한다. 개발 서버만 확인하고 배포 버전도 같다고 단정하지 않는다.
6. 정상 경로 + 안전 차단 + 확대/전체 + PC/모바일 + 키보드 + 변경 후 증거 무효화 + 새로고침 복원을 점검한다.
7. 시각 수정은 스크린샷을 직접 보고 결합점·가림·상태 차이를 확인한다. DOM/단위 테스트만으로 완료 처리하지 않는다.
8. `DEVELOPMENT_DIRECTION.md`에 실제 완료와 남은 한계, 테스트/배포 여부를 기록한다.

명령 예시:

```powershell
node --experimental-strip-types --test scripts/curriculum.test.mjs scripts/tripod.test.mjs scripts/mount.test.mjs scripts/counterweight.test.mjs scripts/tube.test.mjs scripts/observing-setup.test.mjs scripts/alignment.test.mjs scripts/focus.test.mjs
pnpm build
pnpm start --port 3002
```

포트가 사용 중이면 기존 서버 소유를 확인하고 다른 포트를 쓴다. 사용자 서버를 임의 종료하지 않는다. 파일 수정은 apply_patch를 사용한다.
